0.2 HOW FOUR PEOPLE BUILD THIS IN PARALLEL (READ THIS FIRST)
------------------------------------------------------------

This is the most important section in the document. Revision 1 of this plan was a strict
sequence: shell, then schema, then auth, then canvas, then branching, then AI. With four
people that plan idles three of them for two days and then produces a merge catastrophe.

The unblocking mechanism is two files that Rahat writes in the FIRST HOUR of Day 1:

  src/lib/types/schemas.ts    Zod schemas + inferred TS types for every domain object.
  src/lib/demo/fixtures.ts    The entire flooded-city demo, hand-written as typed objects
                              conforming to those schemas.

And one rule:

  NOBODY IMPORTS FROM @supabase ANYWHERE EXCEPT src/lib/db/*.

Every screen, every component, every AI prompt reads data through `src/lib/db/queries.ts`,
which on Day 1 simply returns fixtures:

    // src/lib/db/queries.ts - Day 1
    export async function getBranchScenes(branchId: string): Promise<SceneWithVersion[]> {
      if (USE_FIXTURES) return fixtures.scenes.filter(s => s.branch_id === branchId);
      return realQuery(branchId);   // Rahat fills this in on Day 2-3
    }

Consequences, all good:
- Omit builds the entire workspace on Day 1 against real-shaped data with real content.
- Farin builds prompts and the canon-context builder against fixtures, with no DB dependency.
- Firdosi builds Character Studio and the diff view against fixtures.
- Rahat swaps the implementation underneath them with zero changes to anyone's components.
- The fixtures file ALSO feeds the seed script, so the mocked UI and the seeded database show
  byte-identical content. No "works with mocks, breaks against Postgres" surprise on Day 4.

USE_FIXTURES is an env flag (NEXT_PUBLIC_USE_FIXTURES=1). Keep it working all the way to the
end - it is also the offline demo fallback if Supabase has a bad night during recording.

THE HARD DEADLINE: schemas.ts and fixtures.ts must be pushed to `develop` by end of Day 1
morning. Everything else on Day 1 is secondary to this. If Rahat is blocked on anything, he
drops it and finishes these two files.


1. THE ONE SENTENCE THE BUILD MUST SATISFY
==========================================

"A creator locks a character, builds a short scene sequence, branches at a decision point, a
collaborator changes the branch, AI catches a concrete continuity contradiction with evidence,
the creator selectively merges, and the branch tree and history update."

If a task does not move that sentence forward, it is not a Day 1-4 task.

Demo story - FIXED. Do not redesign it later:
- Character: Wren, a young explorer. Locked reference sheet.
- Prop: a glowing brass compass.
- Location: a flooded city.
- Canon scenes: S1 arrival -> S2 finds the compass -> S3 the choice -> S4 outcome.
- The choice: pursue the compass, or save a trapped stranger.
- Canon branch (main): Wren pursues the compass.
- Alternate branch (what-if/save-the-stranger): a collaborator makes Wren save the stranger,
  which means Wren GIVES THE COMPASS AWAY in the modified S3.
- The planted contradiction: the collaborator's new S4 still shows Wren using the compass.
  The inspector must catch exactly this, cite S3 as evidence, and name the broken canon fact
  "the brass compass is in Wren's possession".

Those 15 seconds are the most important in the video. The data model exists to make that
contradiction detectable from structured fields, not from prose.

---------------------------

- Sidebars collapse; each has a toggle; state persists in localStorage.

4. DATA MODEL (MVP SUBSET)
==========================

The PRD lists 21 entities. The MVP needs 11. Do not create the rest.

  profiles           id (=auth.users.id), display_name, avatar_url
  projects           id, owner_id, title, premise, visual_style, format, created_at
  project_members    project_id, user_id, role ('owner'|'collaborator'|'viewer')
  branches           id, project_id, name, parent_branch_id, branched_from_scene_id,
                     is_canon bool, state ('draft'|'under_review'|'approved'|'merged'|
                     'abandoned'), created_by, created_at
  characters         id, project_id, name, summary, locked_version_id (nullable)
  character_versions id, character_id, version_no, image_url, palette jsonb, traits jsonb,
                     clothing_rules text[], created_by, created_at
  scenes             id, project_id, branch_id, order_index, title, current_version_id,
                     forked_from_scene_id (nullable)
  scene_versions     id, scene_id, version_no, panel_image_url, setting, time_of_day,
                     characters_present uuid[], dialogue text, action text,
                     emotional_beat text, story_purpose text,
                     props_used text[],        <-- the contradiction is detected from here
                     author_id, created_at
  world_facts        id, project_id, branch_id (null = canon), kind ('character'|'prop'|
                     'location'|'rule'|'event'), subject, statement,
                     established_in_scene_id, status ('canon'|'branch'|'draft'|'rejected')
  ai_reviews         id, project_id, branch_id, kind ('continuity'|'merge'), status,
                     findings jsonb, model, created_at
  merges             id, project_id, source_branch_id, target_branch_id,
                     selected_scene_version_ids uuid[], reviewer_id, explanation, created_at
  activity_events    id, project_id, branch_id, actor_id, kind, subject_id, summary,
                     created_at

KEY DECISIONS - do not drift:

1. A branch owns its own rows in `scenes`. Branching = copy the scene rows, point the copies
   at the new branch_id, keep order_index, set forked_from_scene_id. Simpler and far more
   debuggable in five days than a commit DAG, and still honest: history lives in
   scene_versions and activity_events.

2. `props_used` on scene_versions plus prop `world_facts` is what makes the continuity check
   CONCRETE instead of vibes. Canon: "Wren carries the brass compass, established in S2."
   Alternate S3 establishes "Wren gave the compass to the stranger." Alternate S4 still lists
   'brass compass' in props_used. Hard evidence to cite, and deterministically detectable.

3. Exactly one branch per project has is_canon = true. Merging never rewrites history: it
   copies selected scene_versions onto canon as NEW versions and writes a `merges` row.

4. Every mutation writes an activity_events row in the same transaction. The activity feed is
   a required demo beat; retrofitting it on Day 4 is painful.

RLS, minimum viable:
- Read: the user has a project_members row for that project.
- Write: role in ('owner','collaborator').
- The "simulated collaborator" is a REAL second seeded account, not a bypass. Log in as them
  in a second browser profile for the demo. More convincing, and it avoids putting a
  service-role key anywhere near the browser.

STAGED SEEDS - build this, it is your insurance policy:
  npm run seed -- --stage=base       project, Wren (2 versions, unlocked), main S1-S4, facts
  npm run seed -- --stage=branched   + the alternate branch with the collaborator's edits
  npm run seed -- --stage=reviewed   + a persisted ai_reviews row with the compass finding
  npm run seed -- --stage=merged     + the completed merge and activity trail

The live demo performs the transitions between stages. If a take breaks halfway, you jump to
the next stage in ten seconds and keep recording instead of restarting the whole run.


5. THE SHARED CONTRACT
======================

src/lib/types/schemas.ts. Zod is the source of truth; TS types are inferred from it.
Owner: Rahat. Due: Day 1, morning. Three people are blocked until it lands.

  ProjectSchema, BranchSchema, SceneSchema, SceneVersionSchema, CharacterSchema,
  CharacterVersionSchema, WorldFactSchema, ActivityEventSchema

  CanonContextSchema - what goes to the model:
      { project: {title, premise, visual_style},
        lockedCharacters: [{name, traits, clothing_rules, palette}],
        canonFacts:  [{kind, subject, statement, established_in}],
        branchFacts: [{...same, branch}],
        scenes: [{order, title, setting, time_of_day, characters_present, props_used,
                  action, dialogue}] }

  ContinuityFindingSchema - what comes back:
      { id, severity: 'high'|'medium'|'low',
        kind: 'prop_state'|'timeline'|'character_knowledge'|'location'|'design_drift'|'rule',
        affected_scene_id, evidence: [{scene_id, quote_or_field}],
        broken_fact: {subject, statement, established_in_scene_id},
        explanation, suggested_fix,
        source: 'rule'|'model'|'rule+model' }      <-- see section 7, Step A3

  MergeStrategySchema:
      { id, label, description, includes_scene_version_ids, tradeoffs, canon_impact }

  MergeAssistantResponseSchema:
      { source_summary, target_summary, compatible_changes[], true_conflicts[],
        strategies: MergeStrategy[1..3] }

Rules that keep this from rotting:
- API routes Zod-parse their input AND the model's output. Never render raw model text.
- On parse failure: one repair retry, then the deterministic path. Never a stack trace on
  screen during the demo.
- Fixtures, the seed script, and the real queries all satisfy the same schemas. If they
  diverge, the schema is wrong, not the data.

A2  canon-context.ts - build a CanonContext for (project, branch) from queries.ts. Must keep
    canon facts and branch facts separate.
    DEPS: P1, P2.  DONE: a unit test asserts the exact CanonContext for the fixture branch.

A3  THE CONTINUITY INSPECTOR - two-stage, see the note below.
    Stage 1, rules.ts: walk scenes in order_index, track prop possession from world_facts and
    props_used, emit candidate violations with hard evidence (scene ids, field names).
    Stage 2, the model: hand watsonx the candidates plus the CanonContext and ask it to
    explain, assign severity, and propose a fix, returning JSON matching
    ContinuityFindingSchema.
    DEPS: A1, A2.  DONE: the alternate branch yields a high-severity prop_state finding citing
    S3 and the compass fact, with and without the model available.

    WHY TWO STAGES - this is a revision from plan v1 and it matters:
    Rules alone look like a hardcoded if-statement to a judge. A model alone is unreliable at
    state tracking across scenes and will sometimes miss the contradiction on the take that
    counts. Splitting them gives each the job it is actually good at: deterministic state
    tracking finds the violation, the language model explains it in narrative terms and
    proposes the fix. It also degrades gracefully - if watsonx is down, the finding still
    appears with a canned explanation and source:'rule'. Document this split in the README; it
    is a genuine architecture decision, not a fallback hack, and it reads as one.

14. WHAT CHANGED FROM REVISION 1, AND WHY
=========================================

Revision 1 of this file was written as if one person were building. Six substantive changes:

1. RESTRUCTURED FROM A SEQUENCE INTO FOUR PARALLEL TRACKS. The old Steps 1-9 were a strict
   chain; with four people that idles three of them for two days. Tracks P/W/A/C with explicit
   cross-dependencies replace it.

2. ADDED THE FIXTURES LAYER (sections 0.2 and 6). This is the change that makes parallelism
   real. Revision 1 had the UI waiting on Supabase. Now everyone codes against typed fixtures
   from hour one, and the same fixtures feed the seed script so mock and real data cannot
   diverge. This also became a second offline demo fallback for free.

3. PROMOTED THE WATSONX SPIKE TO STEP A0, DAY 1 MORNING. Revision 1 buried the first real
   model call at Step 8, i.e. Day 3-4. The single largest unknown in the project was scheduled
   last. Now it is the first thing Farin does.

4. SPLIT THE CONTINUITY INSPECTOR INTO RULES + MODEL (A3). Revision 1 treated the rule engine
   as a mere fallback for the model. That was backwards: deterministic state tracking is
   better at FINDING the contradiction, and the language model is better at EXPLAINING it and
   proposing a fix. Each now does what it is good at, the demo cannot silently fail, and the
   split is a defensible architecture decision for the README rather than a hidden hack.

5. ADDED STAGED SEEDS (section 4). One seed command that only produced the starting state
   meant a broken take restarted the entire run. Four stages mean you jump forward in ten
   seconds and keep recording.

6. DROPPED THE SPINE/SKIN SPLIT AND MOVED CHARACTER STUDIO INTO A FIRST-CLASS TRACK. That
   split was correct for a solo builder rationing time. With a dedicated owner, Character
   Studio runs in parallel from Day 1 and there is no reason to deprioritise the demo's
   strongest 25 seconds. The cut list in section 12 now handles prioritisation instead.

Also: compressed the schedule from 8 days to the 5 that actually remain, added the file
ownership map (section 3) and the shared-file rule, and moved feature freeze to end of Day 4.
